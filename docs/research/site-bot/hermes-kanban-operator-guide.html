WAO · Hermes Kanban

Running your AI tasks without babysitting them

You hand jobs to a shared board. An engine picks each one up, runs the right AI worker, and files the result. This is how to operate that, start to finish.

1. The four words to know

Everything here is just these four things working together.

Boardthe list
A named to-do list stored on your machine. Your current one is sitebot-research. Unrelated work goes on its own board so nothing collides.
Taskone job
A single job on the board — "run this research spec." It carries who should do it and where the output goes.
Profilethe worker
Which AI does the job. waoengineer reads code and writes reports; waocopy writes Hebrew. All run Qwen 3.8 Max now.
Dispatcherthe engine
The loop that actually runs tasks. It wakes on a timer, finds ready jobs, and starts a worker for each. Nothing runs until it is on.
The one rule that trips everyone up: a task sitting in ready is not running — it is waiting for the engine. If jobs never move, the engine is off. That is almost always the problem.

2. Turn the engine on

The engine lives inside the Hermes gateway. First check whether it is already on:

$ hermes status # is the gateway running? $ hermes kanban list # do you see your tasks?

If the gateway is running, you are done — tasks move on their own. If it is off, start it once and leave it:

$ hermes gateway start # starts the gateway + its dispatcher

No gateway available on this machine? Run the standalone engine instead: hermes kanban daemon --force. Use one or the other — never both, or they fight over the same tasks.

3. Watch the work happen

  1. See the board any time

    A snapshot of every task and its status.

    $ hermes kanban list

  2. Follow it live

    A running feed — tasks starting, finishing, or failing as it happens. Ctrl-C to stop watching (this does not stop the work).

    $ hermes kanban watch

  3. Open one task in detail

    The full history, the worker's notes, and why it passed or failed. Use the short id from the list, e.g. t_29c8500f.

    $ hermes kanban show t_29c8500f

  4. Read the result

    These tasks write their reports here. Open them like any file.

    $ ls docs/research/site-bot/

4. What the colours mean

The status word next to each task tells you exactly where it is.

ready — waiting for the engine running — a worker is on it now review — finished, awaiting a check done — complete, output filed blocked / failed — needs you

A healthy task walks left to right: ready → running → review → done. If it lands on blocked or failed, that is the engine asking for a human — open it with show and read the note.

5. When something looks wrong

What you seeWhat it meansWhat to do
Tasks stuck on ready foreverThe engine is off.Run hermes gateway start (Step 2).
A task went failed / blockedThe worker hit a real problem or a guardrail.hermes kanban show <id>, read the reason, fix the spec, then retry.
You want to re-run a taskIt needs another attempt.hermes kanban reclaim <id> to release it, or reassign <id> <profile>.
Something is running awayYou want everything to stop, now.Stop the engine — see Step 7. Tasks freeze where they are; no data is lost.
Same task keeps crashing, log shows HTTP 401 invalid_api_keyThe worker's profile is missing a credential the engine actually reads. See the box below — it is two layers deep and not obvious.hermes kanban log <id> to see the real error under the "protocol violation" label, then follow the fix below.
The 401-that-looks-like-a-crash trap. When a task keeps failing with "worker exited without calling kanban_complete", that message can be a red herring — the worker may have died from a bad API key before it ever got to do anything. Two things to check, in order:
① Wrong variable name. A profile's .env can hold QWEN_API_KEY correctly, yet Hermes' own credential cache (profiles/<name>/auth.json) may be wired to read DASHSCOPE_API_KEY instead — a leftover from an earlier setup. Add both names with the same value to be safe.
② Stale gateway. If the gateway (Step 2) was already running when you edited a profile's .env, it keeps using the old environment for every worker it spawns — editing the file alone does nothing. Run hermes gateway restart after any .env change, then retry the task.
To retry a task after fixing this: hermes kanban unblock <id>.

6. Start a brand-new batch next time

When Lior hands you a fresh set of specs, the whole cycle is three moves:

# 1 — make (or switch to) a board for this batch $ hermes kanban boards create my-new-batch --switch # 2 — add one task per spec. Two things make it actually run (see box below). $ hermes kanban create "short title" --assignee waoengineer \ --workspace dir:/home/eitanya/wao \ --body "Your working dir is the repo. Read handoff/pending/<spec>.md and \ execute it exactly. When done, call kanban_complete with a summary \ (or kanban_block if you get stuck)." # 3 — make sure the engine is on (Step 2). That's it — it runs itself.
The two things every task needs — learned the hard way, both easy to forget:
① --workspace dir:/home/eitanya/wao so the worker can actually see the repo. Without it the task runs in an empty scratch folder, finds nothing, and fails.
② A body that tells the worker to call kanban_complete when done (or kanban_block if stuck). A worker that just finishes and exits is marked crashed.

To hop between existing boards: hermes kanban boards list, then hermes kanban boards switch <slug>.

7. Stop cleanly when you're done

You can leave the gateway running — it is quiet when the board is empty. To stop it deliberately:

$ hermes gateway stop # or Ctrl-C in its window; standalone daemon: just Ctrl-C
Two safety habits. These tasks are read-only research, but make them muscle memory for everything: after a task finishes, run git status to confirm it only added its own report — nothing else changed. And never point a build task's workspace at the live repo without a spec that says exactly what it may touch.

Your batch lives on board sitebot-research · reports land in docs/research/site-bot/ · specs come from handoff/pending/. When in doubt, hermes kanban list tells you the truth about where everything stands.
